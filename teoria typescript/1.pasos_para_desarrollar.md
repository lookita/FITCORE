# 🧠 Cómo Empezar a Desarrollar Solo

Este archivo no tiene código. Solo tiene preguntas que tenés que hacerte, y un orden mental para arrancar.

---

## 🪨 Lo más importante antes de escribir una sola línea

Antes de abrir VS Code, necesitás responder esto en papel o en tu cabeza:

> **¿Qué entidad es la más importante de mi app?**

En ObsidiantFit, todo gira alrededor del **Usuario**. Sin usuario, no hay rutinas. Sin rutinas, no hay ejercicios. Sin suscripción, no hay acceso.

Ese es tu punto de partida. Siempre.

---

## 🗂️ ¿Cómo pensar en carpetas?

Las carpetas no son para organizar archivos. Son para organizar **responsabilidades**.

Preguntate: "¿Qué cosas hace mi app?" y cada respuesta es una carpeta posible.

Ejemplos de preguntas:
- ¿Quién puede usarla? → carpeta `usuarios/`
- ¿Qué pueden hacer? → carpeta `rutinas/`, `ejercicios/`
- ¿Cómo pagan? → carpeta `suscripciones/`
- ¿Con qué servidor habla? → carpeta `api/` o `services/`

**Regla simple**: si una carpeta tiene más de 5 archivos de cosas distintas, probablemente necesitás dividirla.

## 🔑 ¿Por dónde empezar? El Orden Correcto

### Paso 1: Definir los tipos (`type` / `interface`)

Antes de crear páginas o lógica, definí **cómo se ven tus datos**.

Preguntate: "¿Qué propiedades tiene un Usuario? ¿Cuáles son obligatorias?"

Ahí usás lo que aprendiste de `type` e `interface`. No hay código funcional todavía, solo descripciones.

---

### Paso 2: Crear la estructura visual (HTML/CSS primero)

Hacé la página **sin lógica**. Solo estructura y estilos.

Preguntate:
- ¿Qué ve el usuario cuando entra?
- ¿Qué botones hay?
- ¿Qué formularios necesito?

La pantalla no hace nada todavía. Solo se ve bien.

---

### Paso 3: Conectar la lógica (TypeScript)

Ahora sí agregás funciones. Empezá por lo más simple:

- ¿Qué pasa cuando el usuario hace clic en "Registrarse"?
- ¿Qué datos tengo que recolectar del formulario?
- ¿A dónde van esos datos?

Acá usás funciones, parámetros tipados, retornos, todo lo de teoría.

---

### Paso 4: Conectar con el servidor (`fetch`, Promises, async/await)

Cuando la lógica local funciona, la conectás a la API.

Preguntate:
- ¿A qué URL tengo que mandar los datos?
- ¿Qué formato espera el servidor?
- ¿Qué devuelve si todo sale bien? ¿Y si falla?

Acá usás `Promise`, `async/await`, y tu `ApiResponse<T>` de Generics.

---

### Paso 5: Manejar errores

Siempre, siempre, siempre pensá en el caso de fallo.

Preguntate:
- ¿Qué le muestro al usuario si el servidor no responde?
- ¿Qué hago si el formulario está incompleto?

## 🔍 ¿Cómo buscar en internet lo que no sé?

Esta es la habilidad más importante de un desarrollador. Nunca sabés todo.

**Fórmula para buscar en Google/MDN:**

```
[tecnología] + [lo que quiero hacer] + [en qué idioma]

Ejemplos:
→ "typescript fetch POST json"
→ "typescript array filter by property"
→ "typescript interface extends example"
→ "NestJS create module tutorial"
```

**Dónde buscar:**
- **MDN Web Docs** → para JavaScript puro (fetch, array methods, string methods)
- **typescriptlang.org** → para TypeScript específico
- **docs.nestjs.com** → para el backend de ObsidiantFit
- **Stack Overflow** → cuando tenés un error específico, copiá el mensaje de error exacto

**Cómo leer documentación:**
1. Mirá la firma de la función (qué recibe, qué devuelve)
2. Buscá el ejemplo más simple en la página
3. Copialo y modificalo para tu caso
4. Si no entendés un término, buscalo por separado

## 🧩 ¿Qué elementos de la teoría usar para cada cosa?

| Situación | Teoría a usar |
|---|---|
| Describir un Usuario/Rutina | `interface` o `type` |
| Una propiedad puede ser varias cosas | Union Type `\|` |
| Hacer una petición al servidor | `fetch`, `Promise`, `async/await` |
| Esperar a que lleguen datos | `async/await`, `try/catch` |
| Guardar cualquier tipo de dato | Generics `<T>` |
| Actualizar solo parte de un objeto | `Partial<T>` |
| No enviar la contraseña al frontend | `Omit<T, 'password'>` |
| Repetir lógica cada cierto tiempo | `setInterval` |
| Hacer algo después de un tiempo | `setTimeout` |
| Una función que se aplica a todos | Generics + functions |

## 🧠 El Mindset Correcto

**No escribas código que no entendés.**
Si copiás algo y funciona pero no sabés por qué, pará. Buscalo. Entendelo. Después seguí.

**Rompé en partes pequeñas.**
Si algo parece gigante, preguntate: "¿Cuál es la parte más chica que puedo hacer funcionar?"
Hacé esa parte. Después la siguiente.

**Los errores son normales.**
Un error en la terminal no significa que estás haciendo algo mal. Significa que TypeScript te está hablando. Leé el mensaje, identifica el archivo y la línea, buscalo.

**Escribí primero, refactorizá después.**
Primero que funcione aunque sea feo. Después lo hacés lindo y limpio.

## ✅ Tu Lista Mental al Arrancar un Feature Nuevo

1. ¿Qué tipo de dato maneja este feature? → Definí el `type` o `interface`.
2. ¿Cómo se ve? → Hacé el HTML/CSS primero.
3. ¿Qué pasa cuando el usuario interactúa? → Agregá las funciones.
4. ¿Habla con el servidor? → Conectá con `fetch` y `async/await`.
5. ¿Qué pasa si falla? → Manejá los errores.
6. ¿Funciona? → Probalo a mano.
7. ¿Se puede simplificar? → Refactorizá.
